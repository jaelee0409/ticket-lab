# ticket-lab

공연 좌석 예매 시스템 — **기능이 아니라 동시성을 측정하기 위한 실험실.**

기능 구현이 목적이 아니다. 파라미터를 바꿔가며 부하 테스트를 반복해서,
**측정해야만 알 수 있는 값**을 찾는 것이 목적이다.
"Redis가 빠르다" 같은 이미 아는 결론은 여기서 다루지 않는다.

---

## 찾으려는 값 네 가지

| | 질문 | 상태 |
|---|---|---|
| 1 | 경합 강도에 따라 락 전략의 순위가 뒤집히는 지점은 어디인가 | ✅ 측정 완료 |
| 2 | 대기열 통과율의 최적점은 어디인가 (처리량 vs 개인 지연) | 🔨 진행 중 |
| 3 | DB 커넥션 풀은 어디부터 늘려도 소용없는가 | ✅ 측정 완료 |
| 4 | 결제 실패가 섞여도 정합성이 유지되는가 | ⬜ 예정 |

## 측정 결과

전부 이 저장소의 CSV 원본에서 나온 값이다. 폐기한 측정도 함께 남겨두었다.

### 락 전략 — 순위는 좌석 5~10개에서 뒤집힌다

동시 사용자 200명 고정, 좌석 수를 1에서 500까지. 45개 조건 × 3회, 오류율 0.

| 좌석 | 락 없음 | 비관적 | 낙관적 | 원자적 CAS | Redis |
|---:|---:|---:|---:|---:|---:|
| 1 | 48 ms | 118 ms | 52 ms | 63 ms | 317 ms |
| 5 | 65 | 82 | 63 | 75 | 173 |
| 10 | 59 | 57 | 62 | 60 | 88 |
| 100 | 29 | 29 | 30 | 31 | 39 |
| 500 | 28 | 29 | 28 | 28 | 57 |

*p50 응답 시간. 회차 간 편차 23%.*

- **전환점은 좌석 5~10개** (경합률 20~40:1). 그보다 심하면 비관적 락이 줄을
  세워 뒤처지고, 그보다 약하면 넷 다 구분되지 않는다.
- **Redis 분산 락은 어느 구간에서도 이기지 못했다.** 경합이 심할수록 더 불리했다.
  락 대기 시간을 따로 재보니 **응답 시간의 97%가 락 대기**였고(비관적 락은 7%),
  원인은 Redis 락이 트랜잭션 전체와 네트워크 왕복을 감싸 **임계 구역이 83배**
  길기 때문이었다. 커넥션 풀 대기 큐는 양쪽 모두 0으로, 풀은 원인이 아니었다.
- **정합성은 사실상 공짜였다.** 좌석 10개 이상 구간에서 락을 건 셋과 락 없는
  대조군의 성능 차이가 노이즈 안이었다. 대조군은 매 실행마다 좌석을 5~15건
  중복 판매했고, 락을 건 네 전략은 전 구간 0건이었다.

### 커넥션 풀 — 대기는 사라지지 않고 자리를 옮긴다

풀 크기 5~200, DB 코어 4개와 2개로 각각. 18개 조건 × 3회, 오류율 0.

| 풀 | 풀 밖에서 대기 | 커넥션 점유 | 합계 |
|---:|---:|---:|---:|
| 5 | 47.41 ms | 1.00 ms | 48.4 |
| 20 | 18.74 | 1.63 | 20.4 |
| 100 | 8.52 | 9.00 | 17.5 |
| 200 | 0.02 | 16.75 | 16.8 |

- 풀을 40배 키우는 동안 획득 대기는 0으로 사라졌지만 **점유 시간이 정확히 그만큼
  늘어 합계는 변하지 않았다.** 줄이 풀 밖에서 DB 안으로 옮겨갔을 뿐이다.
- **처리량의 무릎은 10.** 5→10에서 +64%, 10→200에서 +4.7%(노이즈 2.5%).
- **큰 풀의 대가는 처리량이 아니라 꼬리 지연으로 청구된다.** 풀 100 이후 p99가
  2코어에서 +34%, 4코어에서 +13% 악화됐다(노이즈 11%).
- `(코어 × 2) + 1` 공식은 4코어에서 9를 예측해 측정값 10과 맞았지만, **코어를
  2개로 줄여 다시 재니 무릎이 그대로 10이었다.** 맞았던 것이 우연이었다. DB CPU가
  상한의 1/4밖에 쓰이지 않아 공식의 전제가 성립하지 않았고, 실제로는 Little's Law
  (목표 처리량 × 점유 시간 ≈ 7)가 측정값을 설명했다.

## 측정을 믿을 수 있게 만든 규칙

숫자를 만드는 것은 쉽고, 믿을 수 있는 숫자를 만드는 것은 어렵다.
아래 규칙은 전부 **실제로 틀린 결과를 내고 나서** 생긴 것이다.

- **노이즈 플로어를 먼저 잰다.** 모든 조건을 3회 반복하고 회차 간 편차를 구한 뒤,
  그보다 작은 차이는 결론으로 쓰지 않는다.
- **오류율 1% 이상인 조건은 측정이 아니다.** 실패한 요청이 가장 빠르기 때문에
  오류율이 높을수록 성능이 좋아 보인다. 2차 실험에서 Redis의 처리량이 10배로
  나왔는데 실제로는 요청의 97%가 연결 실패였다.
- **평균이 아니라 중간값.** 중간값은 실제로 측정된 값이고 평균은 만들어진 값이다.
- **워밍업은 버린다.** JVM은 JIT 컴파일 전후로 다른 성능을 낸다.
- **조건마다 앱을 새로 띄우고 DB를 초기화한다.** 앞 실행이 팔아치운 좌석 위에서
  다음 실행이 시작되면 조건이 달라진다.
- **동작을 바꾸는 것은 전부 환경변수 노브로 만든다.** 이전 측정이 언제든 다시
  재현되어야 한다.
- **폐기한 측정도 저장소에 남긴다.**
  `contention-v1-unfair.csv`(전략마다 지는 경로의 쿼리 수가 달랐다),
  `contention-v2-500vu-errors.csv`(오류율 최대 97%).

### 이 측정의 한계

부하 생성기(k6)와 서버가 같은 머신에서 돌고 DB는 WSL2 안에 있다.
**절대 수치는 이 환경의 값이지 시스템의 능력이 아니다.**
모든 설정이 같은 왜곡을 받으므로 상대 비교와 순위만 결론으로 썼다.

요청당 31.5ms 중 이 실험들이 설명한 것은 17.7ms뿐이다.
나머지 14ms가 어디서 오는지는 아직 모른다.

## 실행

### 1. 인프라

```bash
docker compose up -d --wait
```

PostgreSQL · Redis · Prometheus · Grafana가 뜬다.
리소스 제한은 의도적이다 — 재현 가능한 조건이어야 비교할 수 있다.

### 2. 애플리케이션

```bash
./gradlew bootRun
```

Windows에서는 `.\gradlew.bat bootRun`.
Flyway가 스키마를 만든다. `http://localhost:8080/actuator/health` 로 확인.

### 3. 실험

```powershell
# 락 전략 × 경합 강도
.\loadtest\run-experiment.ps1 -Sweep SEAT_COUNT -Values 1,2,5,10,20,50,100,200,500 `
  -Strategies none,pessimistic,optimistic,atomic,redis -Vus 200 -Label "경합강도"

# 커넥션 풀 크기
.\loadtest\run-experiment.ps1 -Sweep DB_POOL_SIZE -Values 5,10,20,30,50,70,100,150,200 `
  -Strategies atomic -Vus 200 -SeatCount 500 -Label "풀크기-4코어"
```

러너는 조건마다 DB를 초기화하고, 해당 환경변수로 앱을 새로 띄우고,
워밍업을 버린 뒤 3회 측정해 중간값을 CSV에 남긴다.

```bash
python loadtest/plot_strategies.py --max-seats 500
python loadtest/plot_pool.py
```

## 실험 노브

동작을 바꾸는 값은 전부 환경변수로 뺐다. 전체 목록은 `application.yml`에 있다.

| 변수 | 기본값 | 무엇 |
|---|---|---|
| `LOCK_STRATEGY` | `none` | `none` / `pessimistic` / `optimistic` / `atomic` / `redis` |
| `DB_POOL_SIZE` | `10` | HikariCP 최대 커넥션 수 |
| `QUEUE_ENABLED` | `false` | 대기열 강제 여부 |
| `QUEUE_ADMISSION_RATE` | `50` | 초당 입장 인원 |
| `HOLD_DURATION` | `5m` | 좌석 선점 유지 시간 |
| `TOMCAT_MAX_THREADS` | `200` | 톰캣 워커 스레드 |
| `SCHEDULER_POOL_SIZE` | `2` | 스케줄러 스레드 |

## 구조

```
src/main/java/com/ticketlab/
├── auth/            JWT 인증. 필터가 모든 요청을 먼저 본다
├── user/            사용자
├── event/           공연과 좌석. 경합이 일어나는 무대
├── reservation/     ★ 좌석 선점
│   └── lock/        ★ 락 전략 5종 + 지표
├── queue/           대기열 (목표 2, 작업 중)
├── payment/         결제 (목표 4, 예정)
└── common/          보안·에러·로깅 설정

loadtest/
├── reserve.js              k6 시나리오. 좌석 회색처리 모델
├── run-experiment.ps1      조건을 바꿔가며 자동 반복 측정
├── plot_*.py               그래프
└── results/                CSV 원본 + PNG (폐기한 측정 포함)
```

설계 선택 몇 가지:

- **`open-in-view: false`** — 켜져 있으면 커넥션 풀이 아니라 OSIV를 측정하게 된다.
- **낙관적 락에 JPA `@Version`을 쓰지 않았다** — `@Version`은 좌석에 대한 모든
  쓰기에 적용되어 락 없는 대조군까지 보호한다. 대조군이 깨지지 않으면 비교
  기준이 사라진다.
- **트랜잭션 작업을 `ReservationCore`로 분리** — 같은 클래스 안에서 부르면 프록시를
  거치지 않아 트랜잭션이 조용히 사라지고, Redis 락을 트랜잭션 안에서 기다리면
  DB 커넥션을 쥔 채로 놀게 된다.
- **스키마는 Flyway 소유** (`ddl-auto: none`) — 부분 인덱스가 필요하고, 어제와
  오늘의 측정이 같은 스키마 위에서 돌아야 한다.
