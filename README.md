# ticket-lab

공연 좌석 예매 시스템입니다. 그런데 **만드는 것이 목적이 아니라, 재는 것이 목적**입니다.

티켓 오픈 순간에는 수천 명이 같은 좌석 하나를 동시에 누릅니다.
한 자리가 두 명에게 팔리면 안 되니까 어떻게든 막아야 하는데, 막는 방법이 여러 가지입니다.
그리고 **어느 방법이 좋은지는 상황에 따라 다릅니다.**

"어떤 방법들이 있는가"는 검색하면 나옵니다.
"내 환경에서 몇 명이 몰릴 때 어느 방법이 앞서는가"는 재봐야만 나옵니다.
이 저장소는 **후자만 다룹니다.**

그래서 조건을 바꿔가며 부하 테스트를 수십 번 반복하고, 그 숫자들을 전부 남겨두었습니다.
틀렸던 측정도 지우지 않고 남겼습니다.

## 궁금했던 것 네 가지

| | 질문 | |
|---|---|---|
| 1 | 좌석 경쟁이 심해지면 어느 순간 유리한 방법이 뒤바뀌는가? 그 지점은 어디인가 | ✅ 답 나옴 |
| 2 | 대기열에서 초당 몇 명씩 들여보내는 게 가장 나은가 | 🔨 작업 중 |
| 3 | DB 연결 수를 늘리면 계속 빨라지는가. 어디부터 소용없는가 | ✅ 답 나옴 |
| 4 | 결제가 중간에 실패해도 좌석 상태가 어긋나지 않는가 | ⬜ 예정 |

## 알아낸 것

### 1. 좌석을 지키는 비용은 거의 공짜였다

한 좌석이 두 명에게 팔리는 걸 막으려면 성능을 포기해야 할 것 같지만, **아니었습니다.**

아무것도 안 막은 버전은 **실행할 때마다 5~15건을 중복 판매**했습니다.
막은 버전 네 가지는 전부 **0건**이었고, 경쟁이 심하지 않은 구간에서는
**속도 차이가 측정 오차 안**이었습니다.

그러니까 이 구간에서는 안 막을 이유가 없습니다.

### 2. 유리한 방법이 뒤바뀌는 지점은 좌석 5~10개

경쟁의 세기는 **좌석 수**로 조절했습니다. 사람은 200명으로 고정하고 좌석을
1개부터 500개까지 바꿨습니다. 좌석이 적을수록 같은 자리를 노리는 사람이 많아집니다.

| 좌석 수 | 비관적 잠금 | 낙관적 잠금 | 조건부 UPDATE |
|---:|---:|---:|---:|
| 1개 (극심) | 118 ms | 52 ms | 63 ms |
| 5개 | 82 | 63 | 75 |
| 10개 | 57 | 62 | 60 |
| 500개 (약함) | 29 | 28 | 28 |

*절반의 요청이 이 시간 안에 끝났다는 뜻(p50)입니다.*

**좌석 5~10개 사이에서 순서가 바뀝니다.** 그보다 경쟁이 심하면
"미리 자물쇠를 거는" 비관적 잠금이 줄을 세우느라 가장 느려지고,
그보다 약하면 세 방법이 구분되지 않습니다.

사람 수로 환산하면 **한 자리에 20~40명이 몰릴 때**가 갈림길입니다.

### 3. Redis 분산 잠금은 예상과 정반대였다

경쟁이 심할 때는 Redis가 유리할 거라고 예상했습니다. **모든 구간에서 가장 느렸고,
경쟁이 심할수록 격차가 커졌습니다.**

| 좌석 수 | Redis | 가장 빠른 방법 | |
|---:|---:|---:|---|
| 1개 | 317 ms | 48 ms | 6.6배 느림 |
| 10개 | 88 ms | 57 ms | 1.5배 |
| 500개 | 57 ms | 28 ms | 2.0배 |

왜 그런지 따로 재봤습니다. **Redis 방식은 응답 시간의 97%를 "차례 기다리기"에
썼습니다.** DB 잠금은 7%였습니다.

원인은 **자물쇠를 쥐고 있는 시간의 길이**였습니다.

```
DB 잠금      그 좌석을 건드리는 동안만 쥔다           한 명당 0.08 ms
Redis 잠금   [Redis 왕복] 작업 전체 [Redis 왕복]      한 명당 6.9 ms   ← 83배
```

200명이 한 줄로 서면 이 차이가 그대로 곱해집니다.
**DB 한 대로 충분한 상황에서는 분산 잠금을 쓸 이유가 이 데이터에는 없습니다.**

### 4. DB 연결을 늘려도 기다림은 사라지지 않는다 — 자리만 옮긴다

DB 연결은 미리 몇 개 만들어두고 돌려씁니다(커넥션 풀). 이 개수를 5개에서
200개까지 늘려봤습니다.

| 연결 수 | 연결을 기다린 시간 | 연결을 쥐고 있던 시간 | 합계 |
|---:|---:|---:|---:|
| 5개 | 50.65 ms | 1.00 ms | **51.7** |
| 20개 | 18.74 | 1.63 | **20.4** |
| 100개 | 8.52 | 9.00 | **17.5** |
| 200개 | 0.02 | 16.75 | **16.8** |

연결을 40배 늘리자 기다리는 시간은 0에 가까워졌는데, **쥐고 있는 시간이
정확히 그만큼 늘어서 합계는 변하지 않았습니다.**

줄이 없어진 게 아니라 **DB 바깥에서 DB 안쪽으로 옮겨간 것**입니다.
실제 쿼리는 1ms인데 연결을 16.75ms나 쥐고 있는 이유가 그겁니다 —
그 연결이 DB 안에서 다른 쿼리 뒤에 서 있습니다.

처리량은 **연결 10개에서 이미 끝났습니다**(5→10에서 64% 증가, 10→200에서 4.7%).
그리고 연결을 너무 많이 주면 **평균이 아니라 느린 1%가 나빠집니다** —
연결 100개를 넘기면 상위 1%의 응답 시간이 최대 34% 악화됐습니다.

### 5. 널리 쓰이는 공식이 우연히 맞았다

"연결 수 = (CPU 코어 × 2) + 1" 이라는 유명한 공식이 있습니다.
4코어에서는 9를 예측했고 측정값은 10이었습니다. 잘 맞았습니다.

**확인해보려고 코어를 2개로 줄여 다시 쟀습니다. 공식은 5를 예측했는데
측정값은 그대로 10이었습니다.**

한 번만 쟀으면 "공식이 맞다"고 결론 낼 뻔했습니다.
DB가 애초에 CPU 때문에 막힌 게 아니어서 공식의 전제가 성립하지 않았고,
실제 값은 다른 계산(처리량 × 점유 시간)으로 설명됐습니다.

## 이 숫자들을 믿어도 되는 이유

아래 규칙은 전부 **틀린 결과를 한 번씩 내고 나서** 생겼습니다.

**같은 조건을 3번씩 돌리고, 흔들리는 폭보다 작은 차이는 결론으로 쓰지 않았습니다.**
이 환경에서는 처리량 2.5%, 상위 1% 응답 시간 11%가 그 폭이었습니다.

**실패율이 1%를 넘는 조건은 측정으로 치지 않았습니다.**
실패한 요청이 제일 빠르기 때문에, 많이 실패할수록 성능이 좋아 보입니다.
실제로 한 번은 처리량이 10배로 나와서 확인해보니 요청의 97%가 연결 실패였습니다.

**틀린 측정도 지우지 않았습니다.** `results/` 안에 왜 버렸는지와 함께 남아 있습니다.

### 한계

부하를 만드는 프로그램과 서버가 **같은 컴퓨터**에서 돕니다.
그래서 **절대 수치는 이 환경의 값이지 시스템의 성능이 아닙니다.**
모든 조건이 똑같이 왜곡되므로 **순위와 교차점만** 결론으로 썼습니다.

그리고 요청 하나에 31.5ms가 걸리는데 위 실험들이 설명한 건 17.7ms뿐입니다.
**나머지 14ms가 어디서 오는지는 아직 모릅니다.**

## 직접 돌려보기

### 1. 인프라 띄우기

```bash
docker compose up -d --wait
```

PostgreSQL, Redis, Prometheus, Grafana가 뜹니다.
컨테이너마다 CPU와 메모리를 제한해뒀습니다 — 조건이 매번 같아야 비교할 수 있으니까요.

### 2. 앱 실행

```bash
./gradlew bootRun          # Windows: .\gradlew.bat bootRun
```

DB 테이블은 Flyway가 만듭니다. `http://localhost:8080/actuator/health` 로 확인하세요.

### 3. 실험 돌리기

실험 스크립트는 빌드된 jar를 띄우므로 먼저 빌드합니다.

```powershell
.\gradlew.bat bootJar

# 좌석 경쟁을 바꿔가며 잠금 방식 5가지 비교
.\loadtest\run-experiment.ps1 -Sweep SEAT_COUNT -Values 1,2,5,10,20,50,100,200,500 `
  -Strategies none,pessimistic,optimistic,atomic,redis -Vus 200 `
  -Label "경합강도" -Out "loadtest/results/contention.csv"

# DB 연결 수 바꿔가며
.\loadtest\run-experiment.ps1 -Sweep DB_POOL_SIZE -Values 5,10,20,30,50,70,100,150,200 `
  -Strategies atomic -Vus 200 -SeatCount 500 `
  -Label "풀크기-4코어" -Out "loadtest/results/pool.csv"
```

스크립트가 조건마다 이렇게 합니다:

```
DB 초기화 → 그 조건으로 앱 새로 실행 → 워밍업(버림) → 3회 측정 → 중간값을 CSV에
```

워밍업을 버리는 이유는 JVM이 처음 몇 초 동안은 느리게 돌기 때문입니다.

### 4. 그래프

```bash
python loadtest/plot_strategies.py --max-seats 500
python loadtest/plot_pool.py
```

## 실험 손잡이

동작을 바꾸는 값은 전부 환경변수로 뺐습니다. 코드를 고치지 않고 조건만 바꾸기 위해서입니다.
전체 목록은 `application.yml`에 있습니다.

| 환경변수 | 기본값 | 무엇 |
|---|---|---|
| `LOCK_STRATEGY` | `none` | 잠금 방식. `none` `pessimistic` `optimistic` `atomic` `redis` |
| `DB_POOL_SIZE` | `10` | DB 연결 개수 |
| `QUEUE_ENABLED` | `false` | 대기열 강제 여부 |
| `QUEUE_ADMISSION_RATE` | `50` | 대기열에서 초당 몇 명 입장 |
| `HOLD_DURATION` | `5m` | 좌석을 몇 분간 잡아두는가 |
| `TOMCAT_MAX_THREADS` | `200` | 동시에 처리할 요청 수 |
| `SCHEDULER_POOL_SIZE` | `2` | 주기 작업용 스레드 수 |

## 폴더 구조

```
src/main/java/com/ticketlab/
├── auth/            로그인과 토큰 검사
├── user/            사용자
├── event/           공연과 좌석 — 경쟁이 일어나는 곳
├── reservation/     좌석 선점  ★ 이 프로젝트의 핵심
│   └── lock/        잠금 방식 5가지와 측정 지표
├── queue/           대기열 (작업 중)
├── payment/         결제 (예정)
└── common/          보안, 에러 처리, 로깅

loadtest/
├── reserve.js              부하 테스트 시나리오
├── run-experiment.ps1      조건을 바꿔가며 자동 반복 실행
├── plot_*.py               그래프 그리기
└── results/                측정 원본 CSV와 그래프 (버린 측정도 포함)
```

### 눈여겨볼 설계 선택

**`open-in-view: false`** — 스프링 기본값은 응답을 다 만들 때까지 DB 연결을
붙잡고 있습니다. 켜져 있으면 연결 개수 실험이 전부 무의미해집니다.

**낙관적 잠금에 JPA의 `@Version`을 쓰지 않았습니다** — `@Version`은 좌석에 대한
*모든* 쓰기에 적용돼서, 일부러 안 막아둔 대조군까지 보호해버립니다.
대조군이 깨지지 않으면 비교할 기준이 사라집니다.

**DB 작업을 별도 클래스로 분리** — 스프링의 트랜잭션은 객체를 감싸는 방식으로
동작해서, 같은 클래스 안에서 부르면 **에러 없이 조용히 트랜잭션이 사라집니다.**

**테이블 구조는 Flyway가 관리** — 어제와 오늘의 측정이 같은 구조 위에서 돌아야 하고,
JPA가 못 만드는 형태의 인덱스도 필요했습니다.
